# Review checklist

Read this before changing one of these projects. Check the current repository instructions and adjacent code first. Add a short rule and a source link when review reveals a mistake worth preventing on future changes.

## Before opening or updating a PR

- Read the current contribution guide, PR template, and CI workflow. Look at earlier reviews on the same subsystem before implementing. Keep the diff focused and verify the branch comparison, including changelog conflicts and upstream entries.
- Run the commands CI actually runs, including lint, type checks, tests, and every relevant build. A successful build alone does not establish that lint passed. Verify GitHub checks on the pushed SHA and distinguish pre-existing or environment-specific failures from regressions.
- Exercise the current build through its normal entry point. Check the success path, missing inputs, retries after a failure, and the UI after refreshing or switching views as applicable. Verify labels, tooltips, and loading indicators recover together. Cite observed behavior and distinguish it from fixture or unit-test coverage.
- Verify a review finding against current code before changing it. Treat automated findings as leads and use each repository’s own conventions, especially when bot suggestions about dependency versions or workflow policies disagree.

## TornTools

- Open one PR per feature. Use `feat/<feature-name>` for feature branches. Append the feature to its section in the first unreleased changelog entry and preserve existing formatting. Bump related userscripts when applicable. Follow the repository’s rules for author-written PR and issue communications. [Scope review](https://github.com/Mephiles/torntools_extension/pull/1139#issuecomment-6792674947) · [Contribution guide](https://github.com/Mephiles/torntools_extension/blob/master/CONTRIBUTING.md)
- Use `findElement`, `findAllElements`, and `elementBuilder`. Match observed markup with the simplest selector that identifies the right element. Keep required elements required so markup regressions surface. Use TornTools colors and inspect placement alongside native controls. [Faction row review](https://github.com/Mephiles/torntools_extension/pull/1145#pullrequestreview-6014305869) · [Gym review](https://github.com/Mephiles/torntools_extension/pull/1141)
- Read the feature setting in `isEnabled` and use the feature manager’s `storageKeys` and `reload` hooks. Disabling applies after a page reload. Avoid manual setting listeners, mid-session enable checks, and value returns from lifecycle hooks that perform work. Await async work when the caller needs to track it. [Poker review](https://github.com/Mephiles/torntools_extension/pull/1144) · [Faction row review](https://github.com/Mephiles/torntools_extension/pull/1145/files)
- Prefer a page event or typed listener for an existing XHR/fetch response. If a DOM observer is needed, use the smallest relevant container and mutation options. Use existing caches, daily Torn data, migrations, and helpers such as `getUserBar` before adding requests or storage listeners. [Lottery review](https://github.com/Mephiles/torntools_extension/pull/1140) · [Gym review](https://github.com/Mephiles/torntools_extension/pull/1141)
- Check calculations against both a trusted reference and observed results. Verify real edge cases before adding defensive logic. For price suggestions, compare against maintained alternatives and check whether thin listings, outliers, and missing sources make the suggestion misleading. Verify the input and error recovery in the latest build. [Gym example](https://github.com/Mephiles/torntools_extension/pull/1141#discussion_r4576434291) · [Price suggestion review](https://github.com/Mephiles/torntools_extension/pull/1142)
- Prepare WXT types before local checks. Run the workflow’s Oxlint command with `--max-warnings 0`, TypeScript and Svelte checks, and the relevant builds. For live Torn verification, inspect the page and loaded data read-only. [Code-quality workflow](https://github.com/Mephiles/torntools_extension/blob/master/.github/workflows/code-quality-checking.yml)

## Juicer

The main historical source is the automated review on [Juicer #10](https://github.com/AMFI-Disable/Juicer/pull/10). These checks summarize its findings and do not indicate which findings remain open.

- **Commands and processes.** Use structured executable paths and arguments for user input. Reuse the process runner, drain stdout and stderr without deadlocking, check launch errors separately from nonzero exit status, and call completion on every outcome. Bound output buffers and automatic jobs, and give cancellable or legitimately long-running commands suitable limits.
- **Concurrency and UI state.** Keep process and model state on the owning actor, serialize start/stop and polling jobs, and prevent stale results from updating a newer selection. Preserve sensible command-output ordering. Reset busy state on early exits and surface actual success or failure.
- **File and settings safety.** Stage and verify replacements before overwriting executables. Keep backup metadata and files consistent on partial failure, preserve failed items for retry, and use unique snapshot identifiers. Use versioned migrations and seed missing preferences without resetting existing values. Make confirmation text match the real destination or effect. Avoid preselecting destructive actions from fuzzy matches.
- **Validation and permissions.** Check parser field counts before indexing, validate hostnames/IPs and labels used in paths, and use actual repository paths instead of display names. Pass credentials through the approved storage mechanism and surface failed Keychain or Accessibility writes. Keep actions scoped to the selected item.
- **Formats and interface.** Keep supported file types, MIME/extension labels, and actual encoded bytes consistent. Report write and clipboard errors, clamp pagination after filtering or refresh, verify navigation and grouping, and check narrow layouts with long labels. Expose a utility when its advertised flow and result handling are implemented.
- **Workflow and naming.** Check the repo’s current action versions and pinning policy, and keep CI guidance aligned with workflow files. Use lowercase filenames and commit subjects while preserving product identifiers such as BrewStore, JuicerKit, and Juicer Suite in prose. [Workflow reviews](https://github.com/AMFI-Disable/Juicer/pull/6) · [Stale workflow review](https://github.com/AMFI-Disable/Juicer/pull/9)

## Other repositories and upstream contributions

- **RenYing.** Keep sign-in and sign-up credentials out of plaintext persistence and logs. Verify both regular and offline entry points plus shared cloud helpers. Preserve local edits during sync, including both entries when Unreleased changelog edits overlap. Follow the current RenYing branch and commit conventions. [CodeQL review](https://github.com/AMFI-Disable/RenYing/pull/2)
- **AutoPentester contribution reviews.** The reusable lessons are to validate the same configuration path the migration writes, create parent directories before first-run writes, compute scores from the checks actually counted, bound subprocess execution, and keep permissions explicit. [Migration reviews](https://github.com/SALhik/AutoPentester/pull/3) · [Configuration reviews](https://github.com/SALhik/AutoPentester/pull/4)
- **JS.ORG.** Check eligibility before submitting a domain request. The reviewer required a direct connection to the JavaScript ecosystem. Using JavaScript to build a website was insufficient. [Eligibility review](https://github.com/js-org/js.org/pull/12780)
- **GeoFS Extension, OmniSuite, PathDeck, FMG Free MapGenie, and GeoFS LiverySelector.** The PRs in this audit supplied no additional actionable review rules. The GeoFS Extension and OmniSuite records included standard dependency-bot notices.

## Audit coverage

On 2026-11-23, the audit enumerated the 19 GitHub repositories owned by `AMFI-Disable` and combined their PRs with PRs authored by that account in upstream repositories. It retrieved 149 entries across 58 PRs in 11 repositories, including inline comments, review summaries, and PR discussion. Twenty-nine PRs had at least one entry. This scope covers GitHub PR records visible to the authenticated account. Issue-only discussions, commit-only comments, deleted or inaccessible repositories, and other platforms were outside the inventory.
